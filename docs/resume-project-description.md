# FitPlan AI｜简历项目描述

## 一句话项目介绍

FitPlan AI 是一个面向个人健身场景的 AI 健康管理平台，支持热量与营养计算、饮食/运动自然语言记录、7 天计划生成与局部调整、AI 教练上下文对话和钉钉定时推送，采用 React + FastAPI + PostgreSQL 的前后端分离架构，并通过 Docker Compose 部署到阿里云 ECS。

## 简历推荐写法（完整版）

**FitPlan AI｜AI 健身热量与计划管理平台**  
**技术栈：** React 19、TypeScript、Vite、FastAPI、SQLAlchemy、Alembic、PostgreSQL、Docker Compose、Nginx、GitHub Actions

- 负责从产品建模到上线部署，设计并实现前后端分离的个人健身计划管理平台，覆盖用户资料、目标、热量计算、饮食/运动记录、周计划、AI 教练和钉钉通知等核心流程。
- 基于用户身体资料、活动水平和减脂/维持/增肌目标，实现每日热量、蛋白质、碳水、脂肪目标计算；将饮食摄入与运动消耗拆分汇总，实时更新首页剩余热量。
- 设计自然语言记录解析链路，支持一句话同时识别饮食和运动，例如“吃了烧烤，慢跑了十分钟”，分别完成记录、热量估算、运动消耗统计和日报更新，并提供记录撤销能力。
- 实现 AI 教练上下文构建机制，按当前登录用户隔离读取个人资料、目标、生效计划、当日记录和近期聊天，支持 Markdown 渲染、聊天记录持久化、单条删除/批量清空以及局部餐食和训练调整。
- 实现 7 天饮食/训练计划的生成、保存、激活和延迟训练；在保留周计划整体结构的前提下，支持通过 AI 替换指定日期的单顿餐食或调整局部训练安排。
- 集成钉钉群机器人通知，支持用户级 Webhook、加签密钥加密存储、测试推送和基于 Asia/Shanghai 时区的每日定时推送。
- 使用 Docker Compose 编排 PostgreSQL、FastAPI 和 Nginx 前端服务，通过本机端口 18081 配合 1Panel/OpenResty 反向代理，避免与服务器已有网站的 80/443 端口冲突；使用 GitHub Actions + SSH 实现 main 分支提交后的自动部署。
- 针对移动端完成响应式 UI、底部导航、PWA manifest、favicon 和 iOS 主屏幕图标适配，并使用 Vitest、React Testing Library、Pytest 和 Ruff 完成自动化验证。

## 面试口述版

这是我独立开发的一个 AI 健身计划管理项目。它不是单纯的热量计算器，而是把“目标设置、计划生成、真实记录、AI 调整和每日提醒”串成了闭环。

在实现上，我将用户资料、目标、饮食记录、运动记录、计划和聊天记录分别建模，并通过用户 ID 做数据隔离。用户可以直接用自然语言输入，例如“刚刚吃了两个烧烤，慢跑了十分钟”，后端会识别出饮食和运动两类事件，分别计算摄入热量和运动消耗，再更新当天的剩余热量。

AI 教练部分没有直接把所有数据库内容拼接到 Prompt 中，而是单独构建用户上下文，只读取当前用户的资料、目标、生效计划、当天记录和近期聊天；同时保留近期上下文窗口，避免聊天记录过长。对于计划调整，我把“整体重新生成”和“局部调整”分开，用户只修改晚餐时，不会影响其他日期的餐食和训练。

部署方面，使用 Docker Compose 编排 PostgreSQL、FastAPI 和 Nginx，前端容器只监听服务器本机的 18081 端口，再由 1Panel/OpenResty 对外代理。最后通过 GitHub Actions 监听 main 分支，在提交后使用 SSH 调用服务器部署脚本，完成代码拉取、Compose 校验、镜像构建和服务重启。

## 可突出的问题解决能力

### 1. 混合输入造成的统计错误

**问题：** 用户一句话同时包含饮食和运动时，早期逻辑只记录了饮食热量，运动没有进入活动消耗。  
**解决：** 增加混合记录识别结果模型，将 diet 和 exercise 分成独立字段；保存后分别更新食物摄入和运动消耗，并在首页使用“目标 - 摄入 + 运动消耗”计算剩余热量。

### 2. AI 读取不到真实记录

**问题：** AI 只读取了计划菜单，无法区分“计划吃什么”和“实际吃了什么”。  
**解决：** 构建按用户隔离的上下文服务，将个人资料、目标、当前计划、当天真实记录和近期聊天按用途组织后注入 AI 请求；在提示词中明确区分计划记录与实际记录。

### 3. 局部修改影响整周计划

**问题：** 用户只想替换今晚晚餐时，整周计划不应该被全部重写。  
**解决：** 增加局部计划调整路径，根据目标日期和餐次定位单个 PlanDay 的餐食，只更新目标节点，其他日期和训练内容保持不变。

### 4. 生产端口冲突

**问题：** 阿里云服务器上已经运行其他网站，不能直接占用公网 80/443。  
**解决：** FitPlan AI Web 容器只绑定 127.0.0.1:18081，由 1Panel/OpenResty 作为统一入口反向代理；数据库和后端 API 不直接暴露到公网。

### 5. 多种部署方式并存造成重复部署

**问题：** 1Panel 定时任务和 GitHub Actions 同时部署可能造成并发构建。  
**解决：** 使用 GitHub Actions 的 concurrency、服务器端 flock 文件锁和 fast-forward 检查，避免多个生产部署互相覆盖。

## 项目数据与安全表述

简历中建议使用“按用户隔离”“敏感配置加密存储”“JWT 鉴权”等描述，不建议写成“绝对安全”或“医疗级建议”。热量和运动数据属于估算结果，项目定位是个人健身辅助工具，不替代医疗或营养专业服务。
